2. No finding. The inference reads what the writer wrote, and both drift directions resolve safely. A has-load position holding a stray extra-weight row fails the check (weight must be 0.0) → `unfinishedPlaceOf` returns null → the fill/append path runs, which deletes the planned rows it fills or appends fresh — no user row is ever rewritten, because `_holdsWhatItWrites` requires every row at the position to carry the entry's own `loggedAtMs` stamp and exact values, which a user row (different stamp) cannot match. A no-load position missing the extra row is not a state the writers produce (`setObservations` writes the row whenever `!exerciseHasLoad`, value 0 included; `_createPlannedRows` and the phone's own `addEntry` both go through it), and pre-52c importer rows for a no-load exercise hold weight 0 / extra 0 (the wrist had no way to add weight to a push-up before 52d), which the new check matches.
3. No finding. The correction's `index` is the position the rows were written at: in the plain path both creation and correction use `newIndex[entry.entryId]`, and moved entries have their rows re-id'd to the new index before corrections run (:726-738); in the user-rows path corrections use `rows.indexOf(entry)`, derived from the number parsed out of the row ids themselves (`_observationsByIndex`), and entries there never move. So the `obs-<effort>-<index>-extra-weight` probe and the edited id name the same position. No path edits the wrong row.
