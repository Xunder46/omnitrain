## Findings

1. [Blocker] (Q2, D-14211) `watch/watchos/Sources/WatchSessionEngine/WatchSessionEngine.swift:2267` (`noteRefused`) and `WatchConnectivityBridge.swift` `deliver` catch — a rejection's full text can carry a value from the payload, so a number the user chose can reach the log. `SyncProtocolRejection.message` is built by the validator from the offending value: `SyncProtocolValidator.swift:940`/`:947` quote the number (`"expected at least \(trim(minimum)), found \(trim(value))"`), `:922` quotes a rejected string in full via `describe` (`SyncProtocolValidator.swift:1122`, which returns `"\"\(text)\""` for a String). Concrete reach: `rating` is schema-bounded 1..5 (`watch/sync_protocol/schemas/envelope.schema.json:289-293`) and is the user's tapped effort rating; an old-phone/new-watch build mismatch (exactly the case `requireConformingIncoming` exists for) refuses the frame and `frame_rejected` records `"…constraint_violation at payload.entries[0].rating: expected at most 5, found 9"` — under the 120-character cut, so the value survives it. The same text leaks again through `frame_handler_failed`: `WatchEmissionRejected` is `CustomStringConvertible` with `description = message` (`WatchSessionEngine.swift:30-34`), and the bridge's catch records `"\(error)"`, so the thrown rejection's message is logged too. This violates D-14211 ("never … a number the user typed") and makes the doc's absolute claim false (`docs/state_management/watch_diagnostics.md:68-69`). Fix: at `noteRefused` record `"\(type) \(code) at \(path)"` without `message`; in the bridge's `deliver` catch, special-case `WatchEmissionRejected` the same way. Guard: a fixture frame whose `rating` is out of range; assert the recorded detail names `constraint_violation` and the path, and does not contain the value.

2. [Minor] (Q3) `WatchDiagnosticsLog.swift:142-152` — compaction can silently wipe the log. `compact` takes `readAll()`, and `readAll` (`:108-111`) returns `[]` when `Data(contentsOf:)` throws; the rewrite of empty data then *succeeds* atomically, the file is emptied and `lineCount` set to 0. The in-code claim "a failed rewrite leaves the file as it was" holds only for write failures; a transient read failure (or every line failing to decode) erases the owner's post-mortem record at the moment it matters. Fix: skip the rewrite when `kept.isEmpty` and the file was non-empty (or when `kept.count` is far below `lineCount`). Guard: a test that makes the read fail (e.g. replaces the file with a directory mid-run) and asserts the previous content survives.

3. [Minor] (Q3) `WatchDiagnosticsLog.swift:147-151` — if the atomic rewrite fails, `lineCount` stays at the threshold, so every subsequent `note` retries a full-file read plus rewrite until one succeeds: a failed compaction turns each small append into a whole-file operation. Fix: on write failure, set `lineCount = nil` (recount on next use) or back off. Guard: a test forcing one write failure and asserting the next note appends without reading the whole file (or at least that the log keeps working).

4. [Minor] (Q3) `WatchDiagnosticsLog.swift:32` and `:90-97` — the shared `static let iso` is used *outside* the lock by `noteLaunch` (building `previous=…`) while `encode`/`decode` use it under the lock from other threads. `ISO8601DateFormatter` has no documented thread-safety guarantee. In the app the window is narrow (the host notes the launch before the radio handlers are wired), so this is theoretical; a local formatter in `noteLaunch` (or formatting under the lock) removes it. Guard: none practical at unit level; a comment or the local formatter is the fix.

5. [Minor] (Q1, D-14201) `WatchDiagnosticsLog.swift:59-103` with `:137` — compaction runs under the log's lock inside the caller's `note`: on the main thread (scene changes, the sheet) or on the WatchConnectivity delegate queue, the worst case is a full read of ~3300 lines plus an atomic rewrite, which is more than the "one small file append" D-14201 sanctions. Happens once per ~300 events. Fix: perform the rewrite on a background queue, or amend D-14201 to name the compaction cost. Guard: not practical; a decision note suffices.

6. [Minor] (Q5, D-14207) `WatchSessionEngine.swift:1340-1348`, `:1358-1366`, `:1623-1629`, `:2256-2261` — D-14207's letter says the engine notes `frame_rejected` at the four silent validator returns; the code notes `frame_not_sent` at the three outgoing ones (`emitSnapshot`, `emitLifecycle`, the energy emit) and `frame_rejected` only at `requireConformingIncoming`. The behaviour is defensible (the bridge's vocabulary by direction) and `testS14209ARefusedOwnFrameIsRecordedFrameNotSent` pins it, but the plan text now disagrees with the code, and `docs/state_management/watch_diagnostics.md:38-40` attributes `frame_not_sent` only to the bridge, so a maintainer reading the doc cannot learn that the engine also records `frame_not_sent` for its own refused frames. Fix: one doc sentence naming the engine's `frame_not_sent`, and a note against D-14207 recording the refinement. Guard: none needed beyond the existing tests.

7. [Minor] (Q4) `ios/OmniTrain Watch App/ContentView.swift:562` — the summary's phrase mapping keys on `detail == "background"`, and the detail is `"\(phase)"`. No runtime test compiles `ScenePhase` (the app target is not built by `swift test`), so the claim that the interpolation is the bare case name (`active`/`inactive`/`background`) is pinned only as source text by `testS14213TheSceneNoteIsTheFirstStatementOfTheScenePhaseHandler`. If the interpolation ever changed, the headline silently degrades to the raw kind — cosmetic, but unproven. Fix: a one-line test asserting `"\(ScenePhase.background)" == "background"` (compiles on macOS). Guard: that test.

8. [Minor] (Q5) `docs/state_management/watch_diagnostics.md:65` — "Sentry's Apple SDK does not detect crashes on watchOS" is a stronger claim than the plan backs: A-1 establishes only that there is no MetricKit in the watchOS SDK and no Sentry in the watch target; it does not establish what Sentry's SDK can or cannot detect. Fix: align the sentence with A-1 ("no crash hook, no MetricKit in the watchOS SDK, no Sentry in the watch target").
