## Goal (series row 19c; owner 2026-10-08 "19b, c or whatever is good to go"; 2026-10-10 "start the next stage")

While a session is live on the watch, the operating system must keep the watch app running when the wrist is lowered, so the radio keeps delivering what the user logs. The way the platform
grants that to a training app is a workout session registered with the health service. The package already models it (`WatchPlatformWorkout`, `WatchPlatformWorkoutStore`, the modality →
activity-type table `WatchActivityTypes`) and tests it with a fake; **nothing in the app target creates a real one**, and the app target has no HealthKit entitlement, usage strings or
background mode. This plan writes the real store, wires it to the session's life, and sets the app's configuration. It adds no sensor (heart rate, GPS, steps) and no screen.

## Acceptance criteria

1. When the wrist holds an **active** session, a platform workout of that session's activity type is open; when the session is completed, abandoned or gone, it is closed — exactly one begin and one end per session, however often the surface refreshes.
2. A launch that finds a workout a previous process left open ends it, then (if the restored session is active) opens one for the session.
3. A refused or unavailable health permission changes nothing the user sees: logging, rest, the menu and sync all work as today; the workout is simply not open (denial is not failure).
4. The watch app's built product carries the HealthKit entitlement, the two health usage strings and the `workout-processing` background mode (read back from the built product, not only from settings).
5. `swift test`, the watch scheme build and the flutter suite stay green. What only the owner can do — enabling the HealthKit capability for the watch app's identifier with the team's signing, and the lowered-wrist check on a real watch — is listed as **(owner)** in the docs and the QA guide, and the plan does not claim it works on a wrist.

## Decision Ledger (seeded; do not edit, renumber or delete — append only)

- **D-1500** The scope is the workout registration only. Heart rate, GPS, steps, calories and route (`WatchSensorSource`, `WatchSensorRecorder`, `WatchSessionSensors`) stay unwired; `WatchLoggingState(engine:)` keeps `sensors: nil` (`ios/OmniTrain Watch App/ContentView.swift:~72`). Extended-runtime sessions are not used.
- **D-1501** One rule decides what the platform workout should be doing, as a pure function in the package so it is testable off-device: `WatchWorkoutLifecycle.action(session: WatchSessionRecord?, running: WatchActivityType?) -> start | end | none` — `start` iff the session's `status == WatchSessionStatus.active` and nothing runs; `end` iff something runs and the session is not active (completed, abandoned, nil); else `none`. A session change while one runs (a different `sessionId`) is `end` then `start`: the host compares the id it opened the workout for. It lives beside `WatchPlatformWorkout` (`WatchPlatformWorkout.swift`).
- **D-1502** The real store is `HealthKitWorkoutStore: WatchPlatformWorkoutStore` in the app target (`ios/OmniTrain Watch App/`), compiled for watchOS only. `begin(_ activityType: String)` maps the lower-camel `watchOs` name from `WatchActivityTypes` to `HKWorkoutActivityType` (unknown → `.other`), creates `HKWorkoutSession` + `HKLiveWorkoutBuilder` over one `HKHealthStore`, starts the activity and begins collection; `end()` ends the session, ends collection and finishes the workout; `inProgressActivityTypes()` reports what a previous process left open (`HKHealthStore.recoverActiveWorkoutSession`). Every failure (no authorization, unavailable, a thrown error) is swallowed and leaves no session open: the store never throws into the host.
- **D-1503** Authorization is requested once, when the first session is about to open a workout, not at launch: share = the workout type; read = none in this plan. The prompt must therefore never appear before the user starts training.
- **D-1504** Wiring (`WatchAppHost`, `ios/OmniTrain Watch App/ContentView.swift`): the host owns one `WatchPlatformWorkout` over the real store; after `restore()` and after every revision bump it asks `WatchWorkoutLifecycle` what to do and does it, on one serial chain so two refreshes never race a begin and an end. At launch `recoverInProgress()` runs **before** `restore()` (as `WatchSessionSensors.recoverInProgress` documents: "before anything starts").
- **D-1505** Configuration for the watch target in `ios/Runner.xcodeproj/project.pbxproj` (the three configurations around :655-771): a watch entitlements file with `com.apple.developer.healthkit` set to true and `CODE_SIGN_ENTITLEMENTS` pointing at it; `INFOPLIST_KEY_NSHealthShareUsageDescription` and `INFOPLIST_KEY_NSHealthUpdateUsageDescription` with plain-language strings; `WKBackgroundModes` = `workout-processing` (the planner chooses how — an Info.plist fragment merged with the generated one, or the build setting if Xcode supports it — and proves it by reading the built `Info.plist`). The phone app's `Runner.entitlements` is untouched.
- **D-1506** The owner's part, stated and not simulated: enabling the HealthKit capability for `dev.sasha.omnitrain.watchkitapp` (team `S3976AA7K8`) so provisioning signs the entitlement; installing on a real watch; the lowered-wrist check. A simulator build does not need provisioning; a device build will fail to sign until the owner does this — the docs say so in one line. Every such step is marked **(owner)**.
- **D-1507** Out of scope: the sensors above, the Wear client (`lib/watch/sensors/watch_platform_workout.dart` is the Dart twin and stays as is), a settings toggle to turn the keep-alive off, any change to when a session starts or ends, 19b's delivery.

### Appended by the planner (this run) — D-1508…D-1512

- **D-1508** `WatchWorkoutCoordinator` (package, `WatchPlatformWorkout.swift`, beside `WatchPlatformWorkout`) is the only caller of the store, and `WatchAppHost` is the only thing that builds one. It is a plain `final class` — **not** `@MainActor` — so `swift test` keeps compiling the package for macOS (`Package.swift`, `swift-tools-version: 5.9`, no default isolation). It holds the `WatchPlatformWorkout` it drives, `openedForSessionId: String?` (the session id it opened the workout for; `nil` when it has none open) and one serial tail: an `NSLock`-guarded stored `Task` exactly as `WatchSensorWrites.enqueue` chains its writes (`WatchSensorRecording.swift:223`), so `refresh` and `recoverInProgress` never overlap and two refreshes produce the calls of one, in order (S-1508). `public func refresh(_ session: WatchSessionRecord?) async` is: (1) if `openedForSessionId != nil` and it differs from `session?.sessionId`, `await platform.end()` and clear the id (D-1501's end-then-start); (2) switch on `WatchWorkoutLifecycle.action(session: session, running: platform.running)` — `.start` sets `openedForSessionId = session?.sessionId` **before** `await platform.start(session)`, `.end` does `await platform.end()` then clears the id, `.none` does nothing. It never throws and never retries inside one session: when the store refuses a begin, `WatchPlatformWorkout.start` still sets `running`, so the next refresh computes `.none` and the next `begin` comes only from a different session id or from a fresh coordinator after a relaunch (S-1505). `public func recoverInProgress() async` awaits `platform.recoverInProgress()` and clears `openedForSessionId`; `WatchAppHost.restore()` calls it as its **first** statement, before `engine.restore()` (S-1503, S-1510). The host drives refresh from a `$revision` sink; a `@Published` publisher emits its current value on subscription, so the sink fires once with the empty session during `init` — that refresh is `.none` and calls nothing (Notes). *Derived from the seeded D-1504 and vetoable:* a relaunch mid-session that still finds the engine's session `active` and a stranded workout open ends the stranded one and opens a second Health workout for the same session, so Health can show two entries for one session (the first from the killed process, with no data). Avoiding that needs a persisted "opened but not closed" marker, which is not in this PR.
- **D-1509** The real store maps exactly the activity names the shared contract carries — `running`, `traditionalStrengthTraining`, `flexibility`, `crossTraining` and `other` (the distinct `watchos` values in `watch/contract/watch_sensor_contract.json:30-71`) — each to the same-named `HKWorkoutActivityType` case, with anything unknown going to `.other`. The mapping is one `switch` over the name string whose labels are exactly `case "<watchOs name>":`, with a `default:` arm naming `.other`, so the source guard of S-1509 can read the label set from the file; the mapping's runtime behaviour on a device is not asserted off-device (the app target has no test target and `HKWorkoutActivityType` does not exist on macOS).

- **S-1501 Idempotent.** Same active session, refresh five times → still exactly one `begin`, zero `end`.
- **S-1502 Closes when the session ends.** Completed, abandoned and nil sessions with a workout running → `.end`, exactly one `end`; a second refresh does nothing.
- **S-1503 Relaunch.** Store reports a stranded `running` workout, restored session active → `recoverInProgress` ends the stranded one first, then exactly one `begin` for the session; order asserted (end, then begin).
- **S-1504 A different session replaces.** Active session A opened a workout; the phone's reset makes session B active (A abandoned) → one `end`, then one `begin`, never two open.
- **S-1505 Denial is not failure.** A store whose `begin` does nothing (permission refused): the host's refresh does not throw, logging a set afterwards stores the observation as usual, and a second refresh does not retry in a loop (it asks again only on the next session). *Red today:* no seam to assert it on.

**Actor isolation.** The package is not main-actor isolated (`Package.swift`, `swift-tools-version: 5.9`), while the app target sets `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` with `SWIFT_APPROACHABLE_CONCURRENCY = YES` (`project.pbxproj:674-675`, and `:720-721`, `:765-766` for Release and Profile).
