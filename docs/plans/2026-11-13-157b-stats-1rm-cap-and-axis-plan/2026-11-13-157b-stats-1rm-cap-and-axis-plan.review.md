## Answers to the brief's five questions
1. **Empty-axis mismatch — OK.** The two walks see the same entries with the same partition. `computeProgressData` feeds `_buildFullRepsForExercises` the `completed` list (stats_progress_service.dart:254-255), which is exactly the sessions with `endedAtMs != null` that `_repsAxisExercises` walks (stats_progress_service.dart:1477-1478); both filter `effortKind != 'set'`, null/foreign exercise ids, and skip `reps <= 0`; both split on `weight > 0` (tally :1492-1493 vs `_processSetEffort` :1798-1824). So `isRepsAxis` true requires bodyweight ≥ loaded + 1 ≥ 1 zero-weight entry with reps > 0, which is exactly what puts a day in `repsDayMap` — `repsTrend` can never be empty on the reps axis. The inverse (axis false while only reps data exists) is the intended tie/majority rule (S-15805, S-15806): the card shows Est. 1RM built from the loaded entries. An exercise outside `topLiftIds` never reaches the axis check (the loop iterates `topLiftIds`, :337). Skipped sets tally nowhere (S-15807), a running session decides nothing (S-15810b).
2. **Other zero-weight readers — Minor (finding 1).** `computeExerciseMetrics` (stats_progress_service.dart:1099) and `progressionSamples` (:1201) both route through `_repsAxisExercises`; `_resistanceValue` receives `isRepsAxis` as a parameter and decides nothing (:1613/:1627). `getAllTimeBestReps` (:2442-2444) and `getAllTimeBests` (:2450) still fill the reps axis from `weight == 0` sets by design (D-7) and do not pick one axis per exercise. The only surface that turns a single bodyweight set into a reps figure on an exercise the card reads as weight-axis is the in-session toast (finding 1).
3. **Cap callers — OK.** Toast: `epley1RM(weight, reps)` (workout_session_screen.dart:1115) is compared against `getAllTimeBestE1RM` (:1121), which computes through the same capped `epley1RM` (stats_progress_service.dart:2328) — both sides capped. Session Summary: the builder computes `bestE1RM` with the capped formula at render time (session_summary_builder.dart:91) and compares against `getAllTimeBestE1RM(excludeSessionId: ...)` (session_summary_service.dart:270-275), also capped; the summary is rebuilt from raw sets, no uncapped figure is persisted (`bestE1RM` exists only on the built model, session_summary.dart:72). Wrist: `getAllTimeBests` (:2448) feeds the `bests_down` frame the phone computes, and the wrist's own estimate is capped identically (S-15810 asserts 140.0-held frames). `_sessionRunningBestE1RM`/`_sessionRunningBestReps` throttles compare capped values within one session. No caller compares a capped result against an uncapped stored value, fixture or wire frame.
4. **Swift/Dart parity — OK.** Dart (stats_progress_service.dart:2272-2275): `reps > kEpleyMaxReps ? kEpleyMaxReps : reps` (Int), then `weight * (1 + counted / 30.0)`. Swift (WatchPersonalBests.swift:216-219): `loadKg * (1 + Double(min(reps, epleyMaxReps)) / 30.0)` with `epleyMaxReps = 12` (Int, :213). Same min semantics, same Int→Double conversion point, same operation order (`t = n/30.0; s = 1 + t; w * s`); both sides are IEEE-754 doubles with correctly rounded division, so results are bit-identical for every `reps >= 1`, `loadKg > 0`. Dart's `weight <= 0 || reps <= 0` → null guard has no Swift counterpart, but the wrist only calls `estimateOneRepMax` on logged sets it already validates (not re-derived here; S-87b guards cover the verdict paths).
5. **Docs — all rows applied, one unnamed edit (see Docs delta block).** Every "verified by" test name cited in the changed doc sentences exists in the diff or was read this run.
