## Goal and acceptance

Mostly invisible. It prevents the occasional "the watch jumped back" (or the phone's live session view jumping back) when two messages cross in the air.

| What happens | Now | After 63 |
|---|---|---|
| Two messages from the watch reach the phone back to back (a logged set, then a rest) | the phone starts handling the second while still busy with the first; their steps can interleave | the phone finishes the first, then starts the second; a message whose handling hangs is given up on after 30 s (reported) so later messages are not stuck behind it |
| Two messages from the phone reach the watch back to back | each becomes its own task; their start order is not guaranteed | one at a time, in the order the radio delivered them |
| An older session state (a queued message delivered late) arrives after a newer one | the watch (or the phone's mirror) applies it and moves back to the older state | it is ignored: nothing changes, nothing is answered |
| The same message delivered twice, or two states stamped the same instant | applied once (unchanged) | unchanged: an equal stamp still applies, as a tie goes to the later arrival for reference data |
| An older state of an earlier workout arrives after the next workout began | the phone's mirror switches back to the earlier workout | ignored, same rule (one newest stamp across workouts) |

Known and left: a device whose clock is set backwards by hand ignores that device's state until its clock passes the old instant (the reference-data rule already has the same limit; documented). The phone still stages the entries a stale watch snapshot carries (they are real observations; only the session state is ignored). Not in this plan: the Dart wrist twin in `lib/watch`; reference-data ordering (already newest-wins by `generatedAt`).

## Facts from the scout (`.work/crew/2026-10-23-63/scout-order.md`; spot-checked against files by the lead: `_dispatch` async Stream listener, `deliver` one `Task` per frame, `applySnapshotExclusive` never compares `sentAt`)

- Phone: `WatchConnectivityTransport.onIncoming` -> `_channel.messages.listen(_dispatch)`; `_dispatch` is `async`, `Stream.listen` does not await it, so a second frame's `_dispatch` starts while the first awaits `handler(frame)` (`lib/core/platform/watch_transport.dart`, `_dispatch`). The handler is the `resolved.onIncoming` closure in `lib/state/watch/watch_sync_wiring.dart` (awaits `requests.handle` / `router.receive`, `push.rebaseline()`, `push.flush()`, `timerPush.flushClears()`).
- Phone state apply: `LiveSessionMirrorState.receive` (`lib/state/watch/live_session_mirror_state.dart`) calls `_reconciler.applyMessage(envelope)`; `SyncSessionReconciler._applySnapshot` replaces status, position, revision, timers wholesale with no stamp compare.
- Watch: `OmniTrainWatchConnectivity.deliver` (`ios/OmniTrain Watch App/OmniTrainWatchConnectivity.swift`) does `Task { @MainActor in await self.receiveHandler?(message) }` per frame; `WatchSessionEngine.applySnapshotExclusive` (`watch/watchos/Sources/WatchSessionEngine/WatchSessionEngine.swift`) parses `sentAt` but never compares it; `current` is "last appended row", and `restore` picks `contents.sessions.max { $0.sequence < $1.sequence }`. The engine serialises only the store-append sections (`WatchAsyncMutex`), not whole frames.
- The envelope's `sentAt` is the SENDER's clock and is on every message (`PROTOCOL.md` Envelope table). Comparing a snapshot's `sentAt` only with earlier snapshots from the same sender needs no clock agreement between devices.
- Fixture sequences: the four reconciliation/valid fixture files that hold more than one `session_snapshot` have non-decreasing `sentAt` (checked by script 2026-10-23), so the new rule does not reject a fixture replay.

## Decision Ledger

- D-1 One rule, both devices: **a `session_snapshot` whose `sentAt` is earlier than the newest snapshot `sentAt` this device has applied is stale and changes nothing**; equal or later applies. One newest stamp per device, across all workouts (not per workout), so an old workout's snapshot cannot revive it.
- D-2 Phone transport (`lib/core/platform/watch_transport.dart`, `WatchConnectivityTransport`): new field `Future<void> _lane = Future<void>.value();` and constructor parameter `Duration handlerTimeout = const Duration(seconds: 30)` (stored `_handlerTimeout`). `_dispatch` (current: `final handler = _handler; if (handler == null) return; _heard.add(_clock()); try { await handler(frame); } catch (error, stack) { _report(error, stack); }`) becomes: the `handler == null` return and `_heard.add(_clock())` stay synchronous at the top (a frame is "heard" when it arrives, not when its turn comes), then `final turn = _lane.then((_) => _handle(handler, frame)); _lane = turn; return turn;` with `Future<void> _handle(WatchInboundHandler handler, Map<String, Object?> frame) async { try { await handler(frame).timeout(_handlerTimeout); } catch (error, stack) { _report(error, stack); } }` (`_handle` never throws, so the lane never fails; a `TimeoutException` is reported like any other failure; the abandoned handler keeps running, as the auto-push's timed-out pass does). The builder uses the file's existing handler typedef name.
- D-3 Phone stale rule (`lib/state/watch/live_session_mirror_state.dart`, `LiveSessionMirrorState`): field `DateTime? _newestSnapshotAt`; `bool isStaleSnapshot(Map<String, Object?> envelope)` = type is `session_snapshot`, `envelope['sentAt']` is a String that `DateTime.tryParse` reads, `_newestSnapshotAt` is non-null and the parsed instant `isBefore` it. In `receive` (current order: validator decision, `_consumedTypes` check, `_namesMirroredSession` check, then `final before = state;`), right after the `_consumedTypes` check: `if (isStaleSnapshot(envelope)) return MirrorOutcome.ignored;` (no `notifyListeners`, no answer). After `_reconciler.applyMessage(envelope)` for a snapshot: `_newestSnapshotAt` = the later of itself and the parsed `sentAt`. The router is untouched: it adopts only on `MirrorOutcome.applied`, and the inbox staging of a stale watch snapshot's entries is kept on purpose (real observations, idempotent).
- D-4 Watch lane (new file `watch/watchos/Sources/WatchSessionEngine/WatchInboundLane.swift`, package, not `#if os(watchOS)` so `swift test` covers it): `public final class WatchInboundLane: @unchecked Sendable` holding an `NSLock`, `private var waiting: [[String: Any]]`, `private var running = false` and the injected `handler: @Sendable ([String: Any]) async -> Void`; `public func enqueue(_ frame: [String: Any])` appends under the lock, and when nothing is running marks `running = true` and starts one `Task { await self.drain() }`; `private func drain() async { while let frame = next() { await handler(frame) } }`; `private func next() -> [String: Any]?` returns the first waiting frame (taking it out by slicing `Array(waiting[1...])`, not a call whose name the append-only guard bans), or sets `running = false` and answers nil, all under the lock. Enqueue order is call order, and the radio's delegate callbacks call it in arrival order on one queue. New function names avoid every verb the append-only source guard bans (checklist r, ac).
- D-5 Watch shell (`ios/OmniTrain Watch App/OmniTrainWatchConnectivity.swift`): `private lazy var lane = WatchInboundLane { [weak self] frame in await self?.receiveHandler?(frame) }`; `deliver` (current l.~143: `Task { @MainActor in await self.receiveHandler?(message) }`) becomes `lane.enqueue(message)`. The doc comment is rewritten to say frames are handled one at a time in arrival order. `receiveHandler` stays `@concurrent` (the host-hop source test pins that shape; the builder reads `WatchHostHopSourceTests` BEFORE editing).
- D-6 Watch stale rule (`WatchSessionEngine.swift`): `private var newestSnapshotAt: Date?`; seeded in `restore` (current: sessions read back, `current` = max sequence) from the stored session rows whose `recordId` has the `snap-` prefix (`Self.snapshotPrefix`): the latest `recordedAt` (which IS the snapshot's `sentAt`). In `applySnapshotExclusive`, right after the `guard let sessionId … let sentAt … else { return nil }`: `if let newest = newestSnapshotAt, sentAt < newest { return nil }` (refused whole, so no entry is stored and no tombstone is cleared: a stale snapshot must not bring back an entry the phone deleted since), and after `storeSessionRow(...)` for the snapshot: `newestSnapshotAt = max(newestSnapshotAt ?? sentAt, sentAt)`. A refusal returns nil exactly as the D-78 foreign-session guard does (the caller reports `false`, nothing is answered).
- D-7 `watch/sync_protocol/PROTOCOL.md` (builder-watch, docs-only run, checklist s): under the reconciliation text that says "A snapshot MUST replace structure, status, position, revision, and timer state" add the stale rule (D-1) and the one-at-a-time handling; plus the clock-backwards limit.
- D-8 Not in this plan: serialising the Dart twin (`lib/watch/session/watch_session_engine.dart` has no mutex), a sequence number on the wire, a phone-side change feed.
