## Answers to the brief's five questions (no finding unless said)

Q1 (consumers after Finish): No consumer breaks. The phone's own Finish dialog refuses to save a nothing-logged workout (`workout_session_finish.dart:14-44`: `getExercisesWithEntries()` counts a never-started-only timer exercise, then `finishWouldSaveNothing()` → `Discard Workout?`), so a session whose only work was never-started timers is discarded, never saved — `finishWouldSaveNothing` is unchanged (D-25703, verified in the diff). Training load (`lib/core/models/training_load.dart:235-243`): the case that could flip — `hasSets=false`, `measured=0`, `hasEfforts` true→false after the drop, which turns "contributes nothing" into the remainder rule — is unreachable through the dialog, because `completedExerciseCount>0` (required to pass the dialog) always leaves either a kept logged set (`hasSets`) or a kept started/finished timer instance (`hasEfforts` or `measured`); wrist-involved sessions keep their efforts (`keepEfforts`). Stats (`stats_progress_service.dart:976-999`) counts only `finished` instances with a real duration; a never-started instance contributed 0 before and a deleted one contributes nothing now — no double count, no loss. Summary (`session_summary_service.dart:408-449`) sums `elapsedMs` (0 for `notStarted`, `docs/data_models.md:98`) — unchanged figures; the summary's "nothing logged gives nothing" rules (`docs/session_summary.md:110-118`) already give an emptied exercise no row. History/calendar: no reader requires ≥1 exercise; the shape "timer exercise with no entries" pre-exists (the logger's own `deleteEntry` of a last entry leaves the effort, `session_core_entry.dart:736-748`). Health write runs only for saved sessions and the emptied exercise is simply absent from it.

Q2 (rolling and routine sessions): No misleading comparison. Plan 246's comparison (`session_summary_service.dart:452-`) compares group stats, not exercise lists; a never-started interval contributed 0 ms to the cardio group before, so figures match across the change. Plan linkage (`completePlanFor`, via `onSessionEnded`) keys on routine + day, not exercises. Rolling sessions return `measured` only (`training_load.dart:220`) and are unaffected by the effort removal.

Q3 (wrist-run intervals on the phone): A wrist-run interval is never seen as `notStarted` at Finish. Real-time adoption writes `active`/`paused` into the phone's cache (`adoptRemoteWorkTimer` → `adoptRemoteTimer`, `timer_manager.dart:288-312`); a released timer returns to `notStarted` (plan 244) but the wrist's arriving entry fills it and the importer writes `TimedState.finished`/`RoundState.finished` into the store (`watch_session_importer.dart:1743,1786`), after which `refreshHeldEfforts` → `refreshEfforts` re-reads the instances into the cache (`watch_session_adoption_bridge.dart:240-259`, `session_core_io.dart:245-296`). In `endSession` the drop runs behind `afterPendingImports` (imports settle first, `watch_session_inbox.dart:470-474`), so an already-imported wrist interval is finished before the walk. An entry still in flight is not lost either: `keepEfforts` keeps the exercise and the late entry appends. S-25706 covers the keep path.

Q4 (per-delete notifies): See finding 3; no re-entrancy with `endSession`'s own notify (the screen listener is guarded, debounced listeners coalesce, and `_onSessionEnded`/Health run after).

Q5 (assertions and docs): Every timer assertion reads stored counts/ids/entry indexes/states/rest indexes after Finish, so none would survive a sets-only drop. Docs: the three sentences match the code and their cited tests exist (`S-25701..S-25706`, `S-25704`, `S-25710` all present in the new test file); `docs/session_summary.md:110-118` and `:24` stay true; no other current sentence outside `docs/plans`, `docs/history`, `docs/releases` was found false (searched `never started`, `notStarted`, `placeholder`, and Finish/timed phrasings). Findings 4 and 5 are the two doc nits.
