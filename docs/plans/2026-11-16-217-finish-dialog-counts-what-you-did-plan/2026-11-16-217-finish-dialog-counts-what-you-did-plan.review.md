## Answers to the brief's five questions

1. Resumed sessions — OK. The reopen path `loadSessionData` fills the same three caches the same way. No path found where a logged set or a started timed/round effort reads as not done after a reload. The one arrival gap — a wrist set whose rest is in the store but not yet in the caches — is plan Open item 2 (the drop re-reads the store, the count does not), already owner-noted.
2. Effort kinds — OK. Live efforts carry only `set`, `timed`, `round`, `drill` (sources in Finding 2). The code's mapping (set → rests; round → rounds; else → timed instances) is exact for that vocabulary: `drill` rides the timed branch and the loaders fill timed instances for `drill`. `interval`/`amrap`/`note` exist in `BlockTypes` but no writer creates them; see Finding 2.
3. Efforts in blocks and removed efforts — OK. Block efforts are `SegmentEffort`s with a `blockId` in the same `_efforts` lists, so the count and the drop see them identically. Removal paths clean all caches an effort's count reads: `removeExerciseFromSession` (`session_core_entry.dart:731`) deletes the effort and removes it from `_efforts`/`_observations`/timer manager; `deleteSessionBlock` (`session_block_manager.dart:123-140`) does the same for the block's efforts; the drop itself removes an emptied set effort. Each effort sits in exactly one segment list (keyed by its own `segmentId`, appended once); no double-count path found. The one carry-over exposure is Finding 1.

S-21701..S-21703 call `state.completedExerciseCount()`, which does not exist at base — compile failure there, red at base by construction; S-21702 would also fail the skip-marks-count mutant (expects 1), S-21703 the every-non-set-counts mutant (expects 0).
