## Goal and acceptance

A session that was started on the PHONE with a modality (a routine with a Focus, a Home tile, a planned session) runs on the wrist with that modality, the way 125b does for a routine started on the watch:
- The phone's `session_snapshot` carries an optional `modality`, filled from the phone's session row, and omitted when the session has none.
- A wrist that first hears of the session through that snapshot records it with that modality: Apple Health on the watch opens as that Focus's type (Stretching = Flexibility, Resistance = Strength, Cardio = Running, Sports = Other, same table as 125b), a Cardio or Sports session turns location on from the start, and rounds read "Intervals" / "Periods".
- An empty Free workout the user opened on the watch is replaced by the phone's routine as today (no Health workout is open for an empty Free workout: it waits for its first exercise), and the new session opens with the Focus. A watch workout that already has exercises is still never replaced (D-78 unchanged).
- The wrist never loses or swaps a modality it holds: a snapshot without the key, with a different one, or with a bad one leaves the wrist's value as it is.
- An older phone (no key), an older watch (ignores the key), a malformed key: behaviour exactly as today. The snapshot stays one frame per change (no extra frames).
- The phone's calendar already shows the Focus (plan 122); nothing changes there.

## Input-reality checklist (answers)

- **Writers and units:** one writer per side: the phone's session row (`TrainingSession.modality`, a modality KEY, no unit) → `projectSession`; one reader per client. Display names, case variants and padded strings are not keys (S-12592).
- **Lifecycle:** read once, when the wrist row is created, then carried by every later row; a running session keeps its value; a deleted/edited routine cannot change a started session (plan 122 snapshot rule).
- **Settings changing while open:** none involved.
- **Time edges:** stale snapshots are refused whole before any read (D-127), so an old frame never stamps; the first-hearing rule makes order between a keyless and a keyed frame matter only for a session the wrist created itself (S-12595 e).
- **Load cost:** one short string in a frame that is already sent only when the composed payload changes (S-12599 e); no extra read (`session` is already in hand).
- **Wording:** no UI string; docs say "Focus" for the routine's setting and "modality" for the wire field.
- **Slot competition:** the wrist's snapshot apply, an `exercise_push`, a lifecycle and the coordinator's refresh all go through `mutex.exclusive`/the `$revision` sink; the stamp is decided inside the exclusive section (D-12592). The Health workout opens once per session id; a replaced empty Free workout opens nothing (F-6).
- **Waiting readers (rule "as"):** the phone sends the same frames; only a key is added. No spinner, timeout, "no answer" line or retry reads a snapshot differently.
- **Exact-payload readers:** none assert a whole snapshot map (scout Q4); fixture walkers read `manifest.json` (new files registered); `sync_protocol_harness`-based tests reload the schema and pick the property up.
- **Cross-plan state:** 125b's Focus table and 129's `planned_down.modality` already put a modality on planned wrist starts; this plan covers the remaining direction (phone → wrist session).
