## Findings

1. [Major] watch/watchos/Sources/WatchSessionEngine/WatchLoggingPagerView.swift:111 — a swipe that settles while another land is still in flight is dropped when its index equals the engine's not-yet-moved position. Trace: engine on A, user swipes to B → `land(on: 1)` starts, `landing = true`, `pager.land` awaits `menu.jump` (a serialised engine write). Before it completes the user swipes back to A → `land(on: 0)`: `0 != pager.currentIndex` is false (the engine is still on A), so the guard returns and the second settle makes no jump — one jump for two settled pages, against D-2. Task 1 then commits B, `onSurfaceChange()` bumps the host revision, `followEngine()` snaps `selection` from A back to B: the user's back-swipe is silently undone and the page visibly yanks back. The state does not stay stuck apart (the revision bump heals it), but a user action is lost. Fix (smallest): in the `moved` branch, after `landing = false`, re-issue the land when `selection` has moved off the engine's page again (`if selection != pager.currentIndex { land(on: selection) }`), so the newest settled swipe wins. Guard: none possible in `swift test` (view-level); extend the owner's QA step 18 with "swipe and immediately swipe back — the second swipe wins".

2. [Minor] watch/watchos/Sources/WatchSessionEngine/WatchLoggingPagerView.swift:33,50 — `selection` is seeded `0` and only corrected in `onAppear`, so when the logging surface (re)mounts on a session whose current exercise is not the first (e.g. returning from rest mid-session), the pager renders page 0 — a preview card — for one frame before jumping to the current page. Fix: seed the state in `init` from the menu (`_selection = State(initialValue: <current index from menu.rows>)`, the model is built in the same init). Guard: visual only; owner check on hardware.

3. [Minor] watch/watchos/Sources/WatchSessionEngine/WatchLoggingView.swift:74 — the new `pageLabel` doc comment says it is nil "or [when] a session with an effort clock running", but the pager passes `pager.pageLabel` in the locked branch too (WatchLoggingPagerView.swift:85), where `pageCount > 1` renders "2/3" on the locked single page. Fix: reword the comment ("nil when the session has one exercise; the pager keeps the counter on the locked single page"). Guard: none (comment-only).

## Brief questions

1. Stuck-apart: no permanent divergence found. `landing` always resets (nothing in `land`/`jump` throws; unstructured Tasks are not cancelled on view disappearance), the failed-land path resyncs `selection`, and a successful land heals via the `onSurfaceChange` revision bump. The one real defect is the dropped second settle (finding 1). The `followEngine` self-trigger is safe: it writes `selection = pager.currentIndex` and the `land` guard no-ops the echo.
2. `onSurfaceChange()` is called on the success path only (WatchLoggingPagerView.swift:116-117); the bump reaches `pager.currentIndex` because `rows` derives from `menu.rows` on every access (WatchPagerModel.swift:40; WatchMenu.swift:268-276) and both the body re-render and `.onChange(of: revision)` → `followEngine()` re-read it. Verified.
3. The drag is `simultaneousGesture`, so it blocks nothing: taps (minimum 24 pt), the Crown (a separate `digitalCrownRotation` on the live page), the toolbar button and the system edge swipe all still work; at the NavigationStack root there is no back swipe to fight. `guard pager.isLocked` (line 88) keeps a one-exercise session silent, and a one-exercise session never reaches the notice (its `single` branch is the not-locked case). The notice hide path is correct: `noteLockedSwipe` publishes to show it, the delayed `objectWillChange.send()` at `noticeSeconds + 0.1` re-renders it away; the Task retains `pager`, so a disappeared view is harmless, and a second swipe inside the window only re-arms `noticeUntil` (the earlier task's send re-renders while still visible). The lock itself only clears through an action that bumps the revision (a log on the surface, a phone arrival, reachability) — a countdown expiring keeps `timer.state != .stopped` (WatchTimerMath.swift:26-31), so the locked branch cannot go stale with the lock already gone.
4. At most one live page: `page(_:index:)` builds `WatchLoggingView` only for `row.isCurrent`, and `deriveMenuRows` marks exactly one row current (WatchMenu.swift:273). When a live page turns into a preview, the `WatchLoggingView` leaves the ForEach identity and `onDisappear { model.stop() }` (WatchLoggingView.swift:120) invalidates its ticker; the new current page's view starts its own. A one-transaction overlap of two models over the shared `WatchLoggingState` is possible and benign (both tickers only `poll()`, and milestones are consumed once). Verified.
5. Every name in the new doc text exists and was read this run: `WatchPagerModel`, `land(on:)`, `WatchPagerCopy.lockedNotice`/`noticeSeconds`, `WatchExercisePreviewPage`, `WatchLoggingView(pageLabel:)`, `menuState`, all eleven S-6601..S-6612 test names, the S-004 guard, and (46c's section in the same file) S-6501..S-6507 in WatchEngineSerialisationTests/WatchAsyncMutexTests/WatchHostHopSourceTests. The S-3103 guard stays honest in the letter (finding 4 records the wording overstatement). The Dart reader `test/rest_is_count_up_contract_test.dart` was not re-run (brief forbids the suite); inspection of its roots and the added doc text found no rest-countdown wording, so it is not at risk.
