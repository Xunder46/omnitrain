## Brief questions
1. **Period signals.** None still assumes the old meaning, and none can fire on a baseline with no rated work. `modalityMixShift` returns null when `measure != load` or `baseline.isEmpty` (`modality_mix_shift.dart:79-80`), and a non-empty baseline requires rated work in the pre-period blocks (unrated sessions contribute zero load). `fuelVsLoad` requires both periods to measure load (`fuel_vs_load.dart:63`) and never reads the baseline. `_liftRisePercent` returns null when `liftMeasure != load` or `liftUsualLoad <= 0` (`cardio_efficiency_drift.dart:365-366`). Behaviour note, not a defect: because the period's count is now anchored at its end day, a period ending today and the Mix layer read the same count, so the old separation "layer renders but the signal's period measures time" is unreachable for a period ending today — finding 2 is that separation's ghost.
2. **Adapted tests.** No weakened assertions and no numbers changed without re-derivation; every changed expectation carries a comment whose block arithmetic I recomputed (S-1501/S-1503: 5 blocks; S-1510 A: 4, B: 3 — the 3-vs-4 boundary survives in both the service and screen tests; S-1510 D: 5; S-1511: 2; the pulled-back period: 3 for both windows, correctly re-anchored; F-MIX: 7; F-TIME: 3; S-1913: 9). The one real loss is finding 2 (S-1904b's named path). The S-1913 rewrite can no longer distinguish the session one millisecond outside the period from the one inside (both land in block 7), but that distinction is the old anchor's, and the period-membership assertions elsewhere in the test still carry it.
3. **Note vs measure.** They cannot disagree. The note renders only when `!_isLoad && layer.ratedWeeks < kTrainingLoadMinRatedWeeks` (`mix_layer.dart:212`) and the locked line only when `signalsGateMet` is false, i.e. the same `ratedWeeks < 4` on the same payload. When N ≥ 4 but the measure is time (unrated share above the max), the note's condition is false, so neither the note nor the locked line renders — a time measure with no rated-week explanation. That gap is pre-existing (the same condition shape before 99b) and out of this unit's scope; listing it for the owner rather than as a finding.
4. **`_baselineBlockFor` reuse.** `startMs >= ratedFirstMs` is redundant: `_baselineBlockFor` (`stats_progress_service.dart:978-985`) returns null for any `startMs` before `starts.first`, so the `week != null` check alone would exclude it. It is harmless defensive width matching D-17104's stated `[starts.first, endDay + 1 day)` rule — not a finding. `startMs < ratedEndMs` is load-bearing (block 11 would otherwise absorb every later session; the S-17105 twin kills that mutation). Nothing is left unused: `ratedBaselineBlocks` is gone, `endDay` feeds `ratedEndMs`, `ratedFirstMs` feeds the (redundant) guard, and `sustained_high_load.dart`'s unrelated `ratedBaselineWeeks` is untouched (verified: no `ratedBaselineWeeks` remains in `lib/` outside that file).
