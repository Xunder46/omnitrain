## Findings
1. [Major] lib/core/services/watch_session_importer.dart:888-898 — `_plannedSetToFill` compares a rest POSITION against a row-id NUMBER. `if (!rested.contains(group.number + 1)) return group;` — `rested` holds `EntryRest.entryIndex` values (positions, re-keyed by D-1), but `group.number` is the row-id number from `obs-<effortId>-<n>-<metricKey>`, which is never renumbered (G1/G4). After a phone-side middle delete in a live-merge effort the numbers have a hole ({0,1,3,4}) while positions do not, so a logged set after the hole can be returned as the fill target; the fill path then deletes that logged set's rows (fill.rows deleted at :809-813) and replaces it with the wrist set — user-visible data loss on the phone. Worked example: numbers {0,2,3} all logged, rests {1,2,3} → group number 3 is wrongly returned (checks 4∉rested; the correct check is position+1=3∈rested). Fix: iterate groups by position — `for (var i = 0; i < groups.length; i++) if (!rested.contains(i + 1)) return groups[i];`. Guard: an importer test with a number hole (delete a middle set on the phone, then a wrist set arrives) asserting the first UNLOGGED position is filled and no logged rows are deleted.
2. [Major] lib/core/services/watch_session_importer.dart:785-793 — the wrist-delete path ("Deleted since they were imported") deletes the rows and the instance but never re-keys the surviving rests, breaking D-1's positional invariant: after the delete, each surviving set's logged state shifts by one (worked example: positions 0 logged / 1 unlogged / 2 logged, rests {1,3}; wrist deletes position 0 → new position 0 (old 1, unlogged) reads rest 1 → wrongly logged; new position 1 (old 2, logged) reads rest 2 → none → wrongly unlogged). Pre-existing (the 38f diff did not touch this path), but it is the same family as D-11/A7 and the plan's "importer rest handling untouched" is a scope statement, not a ruling that the invariant may be broken. Fix: call the same re-key the phone paths use after the row deletion. Guard: an importer test that wrist-deletes a middle set and asserts the surviving sets' logged state is unchanged.

[Major] test coverage — the `_lastRestPingFiredAt.remove(effortId)` clearing (lib/features/session/workout_session_screen.dart:1366 and :1404) has no test; the prover's mutation for it is unproven (no verdict in the brief). ## Answers to the brief's five questions
- Q1 (open rest after delete): no defect. `rekeyEntryRestsAfterDelete` (lib/state/workout/timer_manager.dart:644-676) removes the rest at deletedIndex+1 cache-first; `_getMostRecentOpenRestKey` (lib/features/session/workout_session_global_timer.dart:83-103) re-scans all rests for `restEndMs == null` every tick/build with no cached index, so a deleted open rest vanishes from chip/strip and a re-keyed open rest is still found (elapsed comes from restStartMs, index-independent). Two open rests in one effort are impossible: `recordRestStart` (timer_manager.dart:756-776) closes all open rests of the effort before creating a new one, and the re-key only removes/re-keys. Screen glue `_deleteSetAt` (workout_session_screen.dart:~1335-1343) computes `deletedRestWasOpen` before the delete and calls `cancelRestNotifications()` + `_lastRestPingFiredAt.remove(effortId)` after both delete paths (:1362-1366, :1399-1404). Round/timed path: deleteRound/deleteTimedEntry notify before the rekey, but the rekey completes in the same async chain before the next frame paints.
- Q2 (Future<bool> callers): no defect. Callers of deleteRound/deleteTimedEntry: session_core_entry.dart:660/:667 (guarded — rekey only when true) and workout_state.dart:232-233/:257-258 facade (Future<void>, discards the bool — compiles, no UI callers). No path deletes a round/timed entry without SessionCore.deleteEntry: screen deletes go through workoutState.deleteEntry (:1362, :1399); the importer's `_deleteInstance` (:1003/:1011) deletes the wrist's own instances — see Finding 2 for its rest consequence.
- Q3 (snapshot restore ordering/id collisions): no defect. restoreSessionSnapshot (lib/state/workout/session_core_lifecycle.dart:305-405): efforts not in the snapshot are deleted (deleteEffort cascades rests); re-created efforts get their rests from the snapshot after createEffort and are NOT in `currentEffortIds`, so the surviving-effort loop cannot post-delete their rests; surviving efforts get deleteEntryRestsForEffort then create — no id collisions. `setEntryRests` is called for every effort during load (session_core_io.dart:102/:173/:245), so `snapshot.entryRests.containsKey(effortId)` is true for every effort existing at snapshot time; edit-created rests are wiped on restore, which matches the snapshot contract. loadSessionData() at :404 refreshes the in-memory cache; late-entry recovery runs after the loops; the importer guards against duplicate rests (_restAt check, rested set).
- Q4 (SetSegmentBar overflow/ellipsis): no RenderFlex overflow possible. The cell is Expanded → Padding(h:3) → SizedBox(height:48) → Align(topCenter) → Column(min) of constant-height children (Container h:6, SizedBox 4, SizedBox h:20) — no flexible child, so no overflow exception at any text scale. Width: 390 dp screen − 40 padding = 350; 5 cells ≈ 70 each − 6 padding = 64 content; "12×100.5" ≈ 8 glyphs × ~6.7 dp ≈ 54 dp < 64 — fits at base scale, no ellipsis. See Finding 4 for the large-text-scale caveat.
- Q5 (other readers of EntryRest.entryIndex): two findings (1 and 2 above), both in lib/core/services/watch_session_importer.dart. Checked and clean: session_summary_service.dart:33-37 reads rests only for durations (restStartMs/restEndMs); stats_progress_service entryIndex sorts are on TimedInstance, not rests; lib/state/watch/ has no other rest readers besides the fixed bridge (:314 uses loggedSetNumbersOf).
