## Findings

[Minor] lib/core/services/watch_session_importer.dart:829-832 — the comment above the placement loop still reads "the first unfinished interval when the wrist logged a timed, hold or round entry (D-1)", which is 43a's rule; 43c replaced it with shared-start → first in-progress → first not-finished. A maintainer reading the loop site alone is told the wrong order. Failing scenario: none at runtime; a doc/comment drift. Fix: reword to the D-1 order (the `_unfinishedInstanceToFill` docstring at :1013 already states it correctly). Guard: none (comment only).
2. [Minor] docs/watch_session_capture.md:381-385 — the duplicate sentence ("An entry for an interval the phone already logged … writes nothing") never says how "the interval the phone already logged" is identified: the plan's D-2 match is a FINISHED interval of the entry's kind whose start is within the same 1000 ms (`_sameStart`), with the own-id exemption. A reader implementing from the doc alone could match any finished interval, or drop the entry's own half-written instance (S-6315's case). Fix: name the 1000 ms start match (and the own-id exemption) in that sentence. Guard: `test/watch_finish_once_test.dart` `S-6314a`/`S-6314b` and `S-6315` already pin the behaviour; docs only.
3. [Minor] lib/core/services/watch_session_importer.dart:843-855 — crash-recovery corner: a pass that crashed after creating the entry's own instance but before finishing it, at a position `unfinishedPlaceOf` cannot read (foreign rows beside it, the S-6315 fixture shape), leaves that instance not-finished; if the phone logs the same interval meanwhile (a finished instance with the same start, different id), the redelivered entry now hits the duplicate rule (`unfinished == null`, own id exempt, phone's instance matches) and is dropped, so the phantom not-finished instance is never repaired — before 43c the redelivery filled it. Narrow (needs a mid-pass kill plus a phone log in between), and the phone's numbers stand either way. Fix: in the duplicate branch, fall through to the fill path when the entry's own instance exists in a non-finished state. Guard: a test seeding the S-6315 fixture with the own instance `notStarted` plus a phone-finished same-start instance, expecting the own instance finished in place.

## Brief questions

1. Duplicate `continue` (:853): nothing after it still owes the ignored entry. `_placed` is set before the `continue`, so a following rest lands on the phone's interval (S-6316) and the end-of-pass corrections pass includes the entry — harmless, because interval corrections key on the entry's OWN instance id (`timedInstanceIdFor`/`roundInstanceIdFor`), which the duplicate case never has, so `_applyCorrections` no-ops; set corrections cannot reach the branch (intervals only). `changed` stays false — right, nothing was written, so no summary recompute or merge naming is owed. `next++` is not consumed — right. `_reindexInstance` is skipped — right unless the entry's own half-written instance exists, which is finding 3. A redelivered duplicate behaves the same: the entry was never written, so it re-enters `now` on the later pass and the duplicate rule fires again (S-6311's second delivery, different messageId, asserts exactly this). A corrected duplicate: a window correction is dropped silently (own instance absent) — consistent with D-2's "the phone's numbers stand".
2. Target choice: yes, arm 2 can fill an interval the phone started itself with an entry for a DIFFERENT interval of the same exercise — whenever the entry's start matches no in-progress interval (out of tolerance), the first in-progress one is filled and the phone's running clock stops. That matches D-1 as written (arm 2: "else the first in-progress interval") and the plan states it, twice: D-1 and S-6304/S-6305b/S-6306b pin it. The acceptance table's row 1 describes only the start-matched case ("the interval whose clock started at the same moment"), so a reader of the table alone could be surprised — the plan's D-1 is the binding statement, no finding.
3. Push trace (finish adopted + new interval in one window): no ordering sends the new timer before the clear, twice, or never. The retire loop runs first and puts the kind in `retired` when the mirror still holds the exact slot+start, which forces `_WristHolds.no` in the wanted loop (so the mirror's earlier-start arm cannot swallow the new timer) and adds the clear; `clears` is always sent before `next` in the same pass (S-6327 pins the order and the count). If the clear's send fails, the ledger is untouched and the next pass offers it again (S-6325); if the new timer's send fails after the clear landed, `_stale` is set, the mirror no longer holds a running timer of the kind, and the next pass sends the new timer alone — never lost, never duplicated (S-6321's second flush asserts one frame total). `_stale` cannot hide a genuinely newer wrist timer for the same slot: the stale match requires the same start instant (`_sameInstant(stale.startedAt, held['startedAt'])`), and S-6329 pins it — a wrist start 2 ms after the cleared one is treated as the wrist's own newer timer and the phone sends nothing.
4. Docs: every claim in the "Why finishing on either device logs once" paragraph matches the code — the 1000 ms (`_sameStartToleranceMs`), the arm order, the duplicate's write-nothing + rest-still-lands, the adopted-timer clear while the mirror holds the exact timer and before any new timer of the kind, "a clear names a kind, not a slot" (clears are per-kind `{kind: null}`; S-6331B pins the wrist side), the D-4 stopped-timer limit and the D-5 both-log limit. Every named test exists with the name given (read this run: `Mock`/`Hive` groups, S-6301, S-6304, S-6305a/b, S-6306a/b, S-6307a/b, S-6311, S-6316, the S-6321–S-6330 groups, S-6341, `testS6331A`–`E`). One omission only: finding 2.
5. Test quality: no new test found weak.
