## Goal and acceptance criteria
Owner QA on real devices (2026-10-08): the phone and the watch ended up in two different live sessions ("kept session-A, did not adopt session-B (this phone already has a session in progress)", the log), logging stopped syncing for good, finishing on the watch left the phone's session screen open and the phone could finish and rate again. Owner rules, verbatim: "on the watch the user shouldn't be able to start a new routine while in progress; on phone there are guards, and starting a new one should trigger sync and reset the watch state to match the phone; on phone they can only start a new session or end the existing one."
- AC-1 With a live session on the watch, the watch cannot start another one (routine or free workout), on any code path.
- AC-2 When the phone starts a session while the watch holds a different live session, the watch's session ends and the watch shows the phone's new session.
- AC-3 When the watch ends the session the phone holds, the phone's open session screen goes to the summary exactly as if it had finished there, with the effort rating the watch captured, and no second rating prompt.
- AC-4 The docs say "the phone is the authority"; the old "each keeps its own" (docs/watch_session_sync.md D-10 text, PROTOCOL.md) is superseded where it contradicts this.
Out of scope (own PRs): delivery while a device is locked/unreachable (19b), the watch menu/navigation (20), timed Start->Log (21).

## Decision Ledger
- D-170 (supersedes 15-series D-10 "each keeps its own") The pair has at most one live session, and when the two disagree the PHONE's wins. The wrist never replaces a session by itself; it ends its own session only when the phone says so (D-172) or the user ends it. Evidence: `WatchSessionAdoptionBridge.consider` keeps the phone's and returns "kept .. did not adopt" (`lib/state/watch/watch_session_adoption_bridge.dart:~100`); the wrist refuses a foreign snapshot while holding an active session with a non-empty ladder (D-78/D-79, `WatchSessionEngine._guardSession` Dart `lib/watch/session/watch_session_engine.dart:700`, Swift `WatchSessionEngine.swift:1618`).
- D-171 The watch refuses to start a session while it holds one with status `active`: enforced IN THE ENGINE (`WatchSessionEngine.createSession`, Swift `WatchSessionEngine.swift:272`, Dart `watch_session_engine.dart:292`), so no start path can bypass it. A refused start returns the held session and emits NOTHING (no `started` lifecycle, no snapshot, no row). `WatchSessionStartPaths.startFreeWorkout` / `startFromRoutine` (Swift `WatchStartPaths.swift:344,356`; Dart `lib/watch/start/watch_session_start_paths.dart`) therefore need no guard of their own, but one active session with NO exercises yet (a free workout waiting for its first exercise: `ios/OmniTrain Watch App/ContentView.swift:169-179` shows the start surface for it) is a live session too: starting a routine on it ADDS the routine's slots to that session (same session id) and Free workout resumes it. Both stacks identical.
- D-172 Phone starts a session => the watch is reset to it. When the phone's push composes session P and the mirror knows a different live session W on the wrist (the session id the wrist last announced: `LiveSessionMirrorState` state / last wrist snapshot or lifecycle), the push first sends `session_lifecycle` `abandoned` naming W (`LiveSessionMirrorState.reportLifecycleFor(W, 'abandoned')`, `live_session_mirror_state.dart:~547`, used by 17a for pending ends), THEN P's `started`/snapshot. The wrist ends W on the lifecycle frame (it names the session the wrist holds, so `_guardSession` accepts it), shows no rating prompt for an abandoned session, and then accepts P (no active session, D-78 does not apply). W's unsynced work is not rescued (it never reached the phone; a known limit stated in the docs). Order matters and is asserted.
- D-173 The wrist's rule is otherwise unchanged: a snapshot for another session while it holds an active one with a non-empty ladder is still refused silently; the ONLY way a phone replaces the wrist's session is D-172's lifecycle frame. The phone ignores a lifecycle/snapshot from the wrist naming a session it does not hold (`WatchSessionAdoptionBridge.onLifecycle` early returns, `watch_session_adoption_bridge.dart:653-655`), as today: a stale W can never end P.
- D-174 A watch end reaches the phone's SCREEN: `onLifecycle` already calls `WorkoutState.endSession()`/`discardCurrentSession()` (`:658-663`) but nothing tells `WorkoutSessionScreen` (`lib/features/session/workout_session_screen.dart`). The screen, when mounted and its session becomes ended or discarded by anything other than its own finish flow, leaves like its own finish does: completed -> the session summary screen (`session_summary_screen.dart`, which already skips the rating prompt when `session.sessionFeeling != null`, `:271`); abandoned -> back out as its own discard does. The wrist's rating is on the session row before the end is applied (`_catchUpSessionRow`, `:674-681`): assert the summary shows it and does not ask again.
- D-175 The phone's own guards stay as they are (it can only end the current session or start a new one): this PR adds no phone UI, no modal, no button (owner standing rule). A phone-side end already reaches the wrist (17a pending ends); this PR does not change it.

### Entries added by the planner (2026-10-08)

- **D-176 (new; D-172's mechanics and its convergence) The reset is ONE shared step, and the pair converges because the wrist answers the request.** The step is owed when a composed session P exists and the mirror's session id is a session *other than P*: `mirror.sessionId != null && mirror.sessionId != composedId && mirror.sessionId != <the phone's own placeholder id, `watchSessionPlaceholder`>`. It is NOT conditioned on `mirror.isActive`: `reportLifecycleFor(W, 'abandoned')` applies locally whenever W is the mirrored session (`live_session_mirror_state.dart:557-560`) and leaves the mirror's id on W, so an `isActive` test would silently drop the retry after the first pass. Frames, in this order, at most one reset per push pass: (1) `session_lifecycle` `abandoned` naming W — before every frame that names P; (2) P's own snapshot (`sendState(composed)`), sent even when it equals the push's baseline, because a wrist holding W has no P yet; (3) `requestSnapshot()`, after (2). `WatchSyncGraph.sync()` already ends with exactly one request, so its reset adds only (1) and (2) and keeps its one request. Convergence is the *answer* to (3): by then the wrist holds P, the answer names P, the mirror's id becomes P, and the debt clears — nothing in the step writes the mirror's own id. Idempotence: a re-sent `abandoned(W)` is refused by `_guardSession` once the wrist holds P (foreign id) or sets a status the wrist already has; the snapshot is applied whole (D-78 no longer applies: no active session). The step never sends `completed` for W — an end the phone never held is not the phone's to announce (17a F6 stays true).
- **D-177 (new; D-171's other exit) A refused start has exactly one exit shape.** `createSession` refuses while the engine holds a session whose status is `active`, whatever the caller passed, and refuses identically for `exercises: []` and for a non-empty ladder: the held record is returned unchanged, no session row is appended, and no `started` lifecycle and no snapshot are emitted. The absorb case is therefore the start path's own ladder edit, not a second engine path: `startFromRoutine` puts the routine's slots into the held active session in template order and emits only what the engine's slot-insert path already emits — no `started` lifecycle, no new frame kind; `startFreeWorkout` emits nothing.
- **D-178 (new; S-175's cadence) The reset has exactly two triggers and no scheduler of its own.** They are the phone's push pass (`WatchSessionAutoPush._pushOnce`, reached from the coalescing debounce and from `flush()`) and the phone's resume catch-up (`WatchSyncGraph.sync()`, wired at `lib/main.dart:438` through `WatchResumeSync`). Both call the same step (D-176). An owed reset is re-sent by the next pass and by the next resume, bounded to one reset per pass, never queued, never timer-driven, never re-tried inside a pass (a transport failure is the pass's reported exception, F4/D-98).
- **D-179 (new; D-174's edges) The screen leaves once, and only for its own session's external end.** `WorkoutSessionScreen` listens to its `WorkoutState` (subscribed in `initState` only when `!widget.editMode`, removed in `dispose`; the second ticker is untouched) and acts on exactly two states of its own session: `currentSession == null` (a discard deleted the row) pops the route the way the empty-session discard does; `currentSession!.endedAtMs != null` pushes the session summary the way `_finishSession` does (`workout_session_finish.dart:91`), with the same arguments, so the summary reads the row as it stands — including the wrist's rating. It ignores a session id other than the one it was mounted for, every notification while its own finish flow is running (`_isFinishingSession`), every notification in `editMode` (a review mount over an ended session must not replace itself with a summary), and every notification after it has begun leaving (leave-once). Nothing in the listener may reach a `notifyListeners()` synchronously from the build phase (`docs/global_conventions.md`, "No state notification during the build phase").
- **D-180 (new; AC-3's "no second prompt") An abandoned lifecycle owes no rating on the wrist.** The wrist's prompt queue is fed only by the wrist's own End control (`WatchEffortRating.end()` → `noteOwedPrompt`); a phone-sent `session_lifecycle` `abandoned` ends the wrist's session through the engine's apply path and appends no rating prompt, so nothing prompts for W. The phone shows none either: the summary it opens skips the prompt when the row already carries a feeling (`session_summary_screen.dart:271`), and the wrist's rating is on the row before the end is applied (`_catchUpSessionRow`, `watch_session_adoption_bridge.dart:674-681`).
- **D-181 (new; AC-4's scope) 17b's D-95 and its S-115 are superseded where they contradict D-170.** `docs/plans/2026-10-06-17b-watch-auto-sync-pr2-plan.md:59,91` stays as a record, but no feature doc may restate "the phone keeps its own" for the both-hold-a-session case: the rule is D-170 + D-172, and the Phase 4 residue sweep proves no such sentence survives. One exception, deliberately out of scope: the rest-timer rule ("each device keeps its own countdown", `docs/watch_session_sync.md:497`) is 18b's territory and is left untouched.

### Entries added by the second planner run (2026-10-08, unlock / app focus)

- **D-182 (new; D-172/D-176's requested form — the wrist asks, and the phone answers out of the same one reset step) The phone answers a wrist announcement naming W from the table below, and the frames it sends are D-176's.** Trigger: a `session_snapshot` on the receive path whose envelope names `W = envelope['sessionId']`. Two pure reads, both taken BEFORE `_mirror.receive(envelope)` (applying W's active snapshot moves the mirror's status off the memory the fourth row needs): `p = await mirror.projectedSession()` — the phone's own live session as a message; it composes from `WorkoutState` with no D-10 naming guard, so it names P even though the arriving frame named W — and `fate = mirror.rememberedFateOf(W)`, the phone's own record that it ended W (below). Rows, first match wins:
  | Row | Condition | The frames the phone sends | Adoption verdict |
  | --- | --- | --- | --- |
  | the phone holds W | `p != null && p['sessionId'] == W` | none — the pair already agrees (D-92's add-only) | `consider`, as today (`alreadyHeld`) |
  | the phone holds another P | `p != null` (it names P) | `abandoned(W)` through `reportLifecycleFor(W, WatchLifecycleState.abandoned)`, then P through `sendState(p)` — two frames, in that order | `consider`, as today: `refusedConflict` and its "kept … did not adopt" line |

  Rules that bind every row: the fate frame names the wrist's OWN session, so the wrist's `_guardSession` accepts it, and it must precede P (a snapshot naming P while the wrist holds an active W is refused — S-172's rule); the "holds another P" row is exactly the pair D-176's step sends, so a wrist answered twice (the push, then its own announcement) sees no new frame shape; a transport failure drops the whole answer — never queued, never retried in place, and the retry is the wrist's next announcement at its next activation (D-183); the answer is composed per call and never cached, and is NOT gated on `owesResetFor` (a stale W announcement can arrive after the mirror's id has already moved to P); the phone never ends a session it would otherwise adopt — owner rule, kept verbatim: "the phone ADOPTS a wrist session when it has none".
  - **The row-four memory.** `rememberedFateOf(String sessionId)` — a pure read on `LiveSessionMirrorState` — answers the fate the phone has announced for that id: its recorded map first, then, for a session the mirror itself holds, the mirror's own non-active status. The record is written by the two places the phone announces a lifecycle for a session, `reportLifecycle` (`live_session_mirror_state.dart:524`) and `reportLifecycleFor` (`:547`), keyed by the id the frame names, and it is NOT cleared by an incoming frame: without that, the wrist's next re-announcement of the same W would land in the last row and the phone would adopt the session it had just discarded. It is memory-only — after a phone relaunch the mirror is the placeholder again, so the same announcement lands in the last row and the phone adopts W (a known limit, Open question 10).
  - **What the request carries.** A wrist holding W does not request anything: it announces W, and `engine.sessionSnapshot()` is non-null whenever a session is held — an empty ladder included. A wrist holding nothing asks with `{'request': 'snapshot'}` (`WatchTransportRequest.snapshotFrame()`, `lib/core/platform/watch_transport.dart:79`) and needs no id on it: the arm's subject is the wrist's own session, which is announced rather than asked about, and a phone holding nothing has nothing to say about it. So **no protocol change is needed for this feature** — no field, no validator, no fixture, no version row; D-182's frames are existing families with existing shapes, which is why the Phase 4 PROTOCOL row gains one clause and nothing else. A case that seems to need an id on the request is an Assumption Log entry plus a `## Feedback` line, not a silent field.
- **D-183 (new; D-96's missing half) Either device becoming active carries the convergence: the wrist then asks.** The wrist's trigger is `catchUp(reachable:)` at the wrist's next unlock or app focus, and its `engine.session != nil` gate comes OFF: a session-less wrist must also ask, because the phone may hold the session the wrist should be in — today a session-less wrist returns before its first send, which is also why the reachability edge alone (D-96) never fetched the phone's P for a wrist whose own session had been discarded. The reachability check and the `NSLock` in-flight guard both stay (Swift `WatchSyncOrchestrator.catchUp`, `watch/watchos/Sources/WatchSessionEngine/WatchSyncOrchestrator.swift:116`): a trigger arriving while a catch-up runs is DROPPED, not queued, and a trigger after it completes runs a fresh one. Cost, accepted and stated: an activation catch-up also issues `requestRoutines(since:)` and replays owed observations, so a session-less wrist redoes its settings/communication pass on every unlock. A wrist holding W announces W and is answered by D-182; a wrist holding nothing asks with `{'request': 'snapshot'}` and installs P; a wrist holding P answers with its own snapshot as it does today (S-172's convergence). The phone's half of "either device" already exists and this run does not touch it (D-178: `WatchResumeSync` → `WatchSyncGraph.sync()`, `lib/app.dart:172-177`, `lib/main.dart:438`).
