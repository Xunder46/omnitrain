## Goal and acceptance

The wrist cannot tell a set is a personal record because it holds no history. 87a adds the phone → watch message that carries each exercise's standing best, defined exactly as the phone's own "Congrats! New PR" toast defines it, and makes the phone send it on every wrist sync.

Acceptance: (1) a `bests_down` message family exists in the sync contract (schema, valid and invalid fixtures, PROTOCOL.md rows, version-history entry) and both validators (Dart `lib/core/sync_protocol/message_validator.dart`, Swift `SyncProtocolValidator.swift`) accept the valid fixture and refuse the invalid ones; (2) the phone builds it from completed-session history with numbers equal to `StatsProgressService.getAllTimeBestE1RM` / `getAllTimeBestReps` for every exercise (one test asserts equality); (3) the phone sends it with every routines request, including when the bundle is skipped because `since` is current; (4) a wrist that does not know the type ignores it (the Swift `receive` default already returns false), so 87a lands without 87b.

## Decision Ledger

- D-1 PR definition is the phone's, not a new one. Weight axis: `epley1RM(weight, reps) = weight * (1 + reps/30)`, null when weight <= 0 or reps <= 0 (`lib/core/services/stats_progress_service.dart:2121`, `StatsProgressService.epley1RM`). Reps axis: sets with weight == 0 and reps > 0 (`getAllTimeBestReps`, `:2220`). Only `effortKind == 'set'`; only completed sessions (`endedAtMs != null`); strict `>` is applied by the consumer (87b), not here.
- D-2 New message family `bests_down`, phone → watch, reference data (the wrist never edits it). Payload (closed): `generatedAt` (envelope timestamp), `bests` = array of `{ exerciseId: string, e1rmKg: number > 0 (optional), repsBest: integer > 0 (optional) }`, each entry carrying at least one of the two, `exerciseId` unique within the frame, `maxItems` 300 (planner: check the largest existing frame, an `exercises_down` batch of 100, and the transport's size limit, and either confirm 300 or split into batches the way `exercises_down` does). An exercise with no completed set appears nowhere in the frame. Load is kilograms, the wire's unit (`watch/contract/watch_logging_contract.json` `unitConversion`; the wrist's set payload field is `loadKg`, `WatchLoggingState.swift:985`).
- D-3 Frame semantics for the consumer (written now so 87b cannot drift): a wrist that holds a `bests_down` and finds an exercise absent from it treats that exercise as having no history (a first-ever set is a PR, as on the phone); a wrist that has never received one announces nothing. The wrist keeps the newest frame (latest `generatedAt` wins, a tie goes to the copy received later), the rule `preferences_down` already follows (PROTOCOL.md, `preferences_down` note).
- D-4 Sending rule: the phone sends `bests_down` with EVERY routines request, after the bundle frames and independent of `since` and of the bundle stamp. Reason: bests change after every completed workout, and the bundle stamp changes only when preferences, foods or routines change (PROTOCOL.md `since` rule; `WatchSyncRequestHandler._sendRoutines`, `lib/state/watch/watch_sync_request_handler.dart:121`). Putting bests into the bundle would resend foods and routines after every workout. A send the radio did not carry is not retried inside the request; the next request sends it again.
- D-5 Computation: ONE pass over completed-session history producing every exercise's bests (new bulk method on `StatsProgressService`, planner names it), not 166+ calls of `getAllTimeBestE1RM`, each of which re-walks the whole history (`:2149`). The bulk result must equal the per-exercise methods for every exercise of the same fixture (S-87a-5). The in-progress session is excluded exactly as there.
- D-6 Not in scope: any wrist detection, store, banner or haptic (87b); any change to the phone's toast or its definition; showing bests anywhere; the Dart twin's `lib/watch/` ingestion (planner: read `lib/watch/session/watch_records.dart` and `docs/watch_session_sync.md` and report under Open questions whether the twin must store it; default is no, because nothing in the Dart twin consumes bests).
- D-7 Additive contract change: no new rejection code, no version change; a v1 wrist that does not know the type ignores it. Record it in PROTOCOL.md's version history the way the 2026-10-23 amendments are written.
- D-8 Open for the owner, not blocking this PR: whether a frame older than some age should stop the wrist announcing PRs. This PR carries `generatedAt` so 87b can decide; 87a ships no age rule.
- D-9 One frame, capped at 300 (answers D-2's planner note). No size limit exists anywhere in this repo's transport layer — `lib/core/platform/watch_transport.dart` and `watch_connectivity_channel.dart` contain no size or limit check, and the underlying plugin (`packages/omnitrain_watch_link/ios/Classes/OmniTrainWatchLinkPlugin.swift`, `sendMessage` :90) passes the dictionary straight to `WCSession`; the platform's documented `sendMessage` payload ceiling (~65 KB) is the only bound and is not enforced here. The largest frame already shipped is a full `exercises_down` batch of 100 catalog exercises; a 300-entry bests frame is ≈ 300 × ~80 B ≈ 24 KB, the same order. So `bests_down` is ONE message, never batched: batching would break D-3 (a wrist applying batch 2 would drop batch 1's entries, because absence from the newest frame means no history). The builder stops at 300 entries, ordered by D-12, so a user with more than 300 distinct trained exercises gets the first 300 by exerciseId and the wrist treats the rest as no history — the same failure class the owner already accepted for a wrist that has never synced. Which exercises win the cap is an owner choice (Open question 3); the schema's `maxItems` 300 stays a receiver-side bound the phone's own frames never violate.
- D-10 No rounding. `e1rmKg` travels at the full double precision `epley1RM` computes (e.g. 116.66666666666667), never rounded: a rounded value could make the wrist's strict-`>` comparison (87b) disagree with the phone's toast for a set within one rounding step of the standing best. Doubles round-trip exactly through JSON on both ends.
- D-11 Send placement. In `_sendRoutines` (`lib/state/watch/watch_sync_request_handler.dart:121`) the exercise-list section (the `heldExercises` early return :171, `buildExercisesDown` + `batches.isEmpty` :186, the `exercisesVersion == version` early return :193, and the batch loop) is extracted into a private `_sendExerciseList` that keeps its early returns; `_sendRoutines` then builds and sends `bests_down` and returns true. Consequences: bests is the LAST frame of the answer; it is sent on every request regardless of `since`, of the bundle stamp, of the exercises-version early return, and of a batch-refusal break; a failed bests send cannot suppress or change the bundle frames' result, and the return value stays `true` on every path (S-87a-7). The frame is built from a fresh `StatsProgressService(_repository)` per request — the service caches one history snapshot per instance (`docs/state_management/services_and_utils.md:243`), so a held instance would serve stale bests and break S-87a-8. This matches the standing construction pattern (`lib/core/services/session_summary_service.dart:258`, `lib/features/stats/stats_screen.dart:111`).
- D-12 Entry order. `bests` entries are ordered by `exerciseId` ascending (Dart string `compareTo`), and the D-9 cap keeps the first 300 of that order. Deterministic, so the frame is stable across requests with unchanged history and the cap has a defined winner.
- D-13 Message id. `messageId: 'msg-bests-<generatedAtMs>'` (the `foods_down` shape, `watch_reference_sync.dart:558`). Edge accepted: two requests in the same millisecond with changed bests share an id, so the wrist may treat the second as a redelivery; the next sync re-sends with a fresh stamp and D-3's newest-frame rule self-heals. (`preferences_down`'s id carries a content discriminator because a setting can change between two requests in one millisecond; bests change only via completed workouts, which are far slower than the clock.)
- D-14 Semantic-layer rules (the schema dialect cannot express them — no `anyOf`, no `exclusiveMinimum`, `oneOf` is exactly-one, `message_validator.dart:84-89` and :1010-1040). Both validators refuse, with `semantic_violation` at `$.payload.bests[i]`: (1) an entry carrying neither `e1rmKg` nor `repsBest` — the seed's S-87a-4 says `constraint_violation`, kept verbatim, raised as Open question 1, because a schema constraint would also refuse S-87a-2's both-axes entry; (2) a duplicate `exerciseId`; (3) `e1rmKg` present and == 0; (4) `repsBest` present and <= 0. Schema-level codes stay: `repsBest: 12.5` → `invalid_type` (`type: integer`), an unknown field → `unexpected_field`, `origin: "watch"` → `invalid_const_value`, 301 entries → `constraint_violation` (`maxItems`).

## Core scenarios (re-derive every number in the first run)

Fixture H (history, all `effortKind` 'set', weights in kg): completed session 1: bench-press 100 x 5, 100 x 3; squat 140 x 5; push-up 0 x 12; plank is a `hold` effort with 0 reps weight 0 hold 60 s. Completed session 2: bench-press 90 x 8. In-progress session 3 (not ended): bench-press 120 x 5, push-up 0 x 20.

- S-87a-1 Builder on H: bench-press `e1rmKg` = max(100 x (1+5/30) = 116.6667, 100 x (1+3/30) = 110, 90 x (1+8/30) = 114) = 116.6667 and no `repsBest`; squat `e1rmKg` = 140 x (1+5/30) = 163.3333; push-up `repsBest` = 12 and no `e1rmKg`; plank is absent (hold, not 'set'); nothing from session 3 (120 x 5 = 140 and 20 reps are NOT in the frame). Red today: no builder exists.
- S-87a-2 An exercise with both axes (bench-press 100 x 5 in one session and 0 x 15 in another) carries both `e1rmKg` and `repsBest`.
- S-87a-3 A user with no completed sessions: the builder returns a frame with `bests: []` and the schema accepts it (an empty frame is a frame: it tells the wrist "you have history knowledge: none", so every first set is a PR).
- S-87a-4 Contract: `fixtures/valid/bests_down.json` conforms in both validators; invalid fixtures are each refused with the stated code: an entry with neither number (`constraint_violation`), `e1rmKg: 0`, `repsBest: 12.5`, a duplicate `exerciseId` (`semantic_violation`), an unknown extra field, `origin: "watch"`. Red today: no schema, so the family is unknown.
- S-87a-5 Parity: for every exercise in H and in the repository's seed data, builder `e1rmKg` equals `getAllTimeBestE1RM(id)` and `repsBest` equals `getAllTimeBestReps(id)` (0 maps to "absent"). Breaks loudly if either side changes (same idea as D-13 of `docs/plans/in-session-pr-toast-plan.md`).
- S-87a-6 Sending: a routines request whose `since` equals the current bundle stamp is answered with none of the three bundle frames AND with one `bests_down` (existing `S-9201`..`S-9212`, `test/watch_sync_changed_only_test.dart`, must still pass unchanged: planner lists which of them count frames and adjusts only by reading, not by loosening). A request without `since` gets the three bundle frames then `bests_down`. Red today: no frame is sent.
- S-87a-7 A transport that does not carry the `bests_down` frame does not fail the request's other frames and does not change the return value the bundle frames' success decides.
- S-87a-8 The frame is built from storage read at request time: a workout completed between two requests changes the second frame (no stale cache of bests, unlike the foods cache of plan 74).
- S-87a-9 Over-300 cap. Fixture: 301 distinct exercises `ex-000`..`ex-300`, each with one completed 'set' effort (reps 5, weight 60.0) in one completed session. Trigger: `buildBestsDown` over that history. Flow: bulk method → builder. Expected outcome: the frame's `bests` has exactly 300 entries, ordered `ex-000`..`ex-299`; `ex-300` is absent. Edge case of: S-87a-1.
- S-87a-10 Both-axes entry on the wire. Fixture: the valid fixture `bests_down_both_axes.json` — one entry carrying both `e1rmKg` and `repsBest` (S-87a-2's shape). Trigger: both validators on the fixture. Flow: the manifest-driven suites. Expected outcome: conforms in Dart and Swift (an entry may carry both; the "at least one" rule is a floor, not an exclusive-or). Edge case of: S-87a-4.
- S-87a-11 The sent frame validates. Fixture: the handler test's seeded repository (any state, including empty history). Trigger: a routines request through the real handler. Flow: capture the sent `bests_down` envelope, run it through `loadProtocolValidator()` (`test/helpers/sync_protocol_harness.dart:63`). Expected outcome: zero rejections — the sender and the contract cannot drift. Edge case of: S-87a-6.
- S-87a-12 `generatedAt` is the request clock. Fixture: the handler test repo. Trigger: two routines requests. Flow: read both frames' `payload.generatedAt`. Expected outcome: each frame's stamp is that request's own clock reading (not a stored bundle stamp), so a second request after a workout carries a later stamp. Edge case of: S-87a-8.
- S-87a-13 Empty history on the wire. Fixture: repository with exercises but no sessions. Trigger: a routines request. Flow: handler → builder. Expected outcome: exactly one `bests_down` frame whose `bests` is `[]` (S-87a-3's frame, sent). Edge case of: S-87a-6.
- S-87a-14 In-progress only. Fixture: one session with `endedAtMs == null` holding a 'set' effort (reps 5, weight 100.0). Trigger: `getAllTimeBests()` / `buildBestsDown`. Flow: the bulk walk. Expected outcome: `bests: []` — the in-progress session's 140 e1RM is not in the frame. Edge case of: S-87a-1.
