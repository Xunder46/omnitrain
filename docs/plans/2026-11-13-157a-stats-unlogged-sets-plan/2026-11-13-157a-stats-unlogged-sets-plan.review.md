Guard: a test with a repository whose `deleteEntryRestsForEffort`/`createEntryRest` fails mid-rekey.

## Answers to the brief's questions

**Q1 — the second Finish route (`lib/features/session/session_summary_screen.dart:492`): OK.** `_finishAndSaveSession` calls `endSession()` only when `!_isHistoricalView` (line 491). Both push sites of `SessionSummaryScreen` hand it an already-ended session: the screen's own finish ends first, then pushes (`lib/features/session/workout_session_finish.dart:88-94`), and the watch-ended listener pushes only when `session.endedAtMs != null` (`lib/features/session/workout_session_screen.dart:335-365`). The calendar route passes `openedFromCalendar: true`, which is the historical view. So `endSession` returns at the `endedAtMs != null` guard (`session_core_lifecycle.dart:15`) before the drop — the summary route can never run the drop, with or without unlogged sets. Even in a hypothetical future route that opened the summary over an open session, the drop is quiet (D-6), the summary computes `_summary` once in `initState` (line 152), and `_finishAndSaveSession` immediately clears the session and pops to the first route — no stale frame is served.

**Q2 — the open screen while Finish awaits: OK.** No out-of-range index is reachable. The drop notifies nothing (D-6: deletes go through `_repository.deleteObservation`, not `deleteEntry`); the single `_notify()` (`session_core_lifecycle.dart:76`) fires while the screen is mounted, but `_finishSession` sets `_isFinishingSession` synchronously before awaiting `endSession` (`workout_session_finish.dart:67`), and the screen's listener returns early on `_isFinishingSession` (`workout_session_screen.dart:339`) — so the notify reaches no reader of `_currentSet`/`_exercises`. The screen's entry lists are its own `_exercises` snapshot (`workout_session_screen.dart:630-632`), which the drop never mutates, and its accessors clamp: `_getEntryData` bounds-checks (727-729), `_focusExerciseDetail` bounds-checks (745-747) and clamps the set number (758-765), `_exerciseIdForIndex` bounds-checks (731). What S-15709 covers (`test/finish_drops_unlogged_sets_screen_test.dart`): the real dialog flow (tap Finish, confirm), no exception, the summary replaces the screen, the repository holds exactly the logged set, the summary totals and the SETS pill show 1. It does not cover an exercise removed from the state while the screen is focused on it (every set of the focused exercise unlogged), and not the failure path; both are unreachable as index errors because no notify reaches the screen mid-drop and the snapshot is untouched — noted, not a finding.

**Q3 — a mid-drop throw: Minor (finding 2).** Within one position, a `deleteObservation` throw leaves the store holding a partial set, but `rows.removeWhere` has not run, so positions are unshifted and the rekey is correctly not called — the leftovers read as a set, today's behaviour, self-consistent. A throw between efforts leaves earlier efforts pruned and later ones with placeholders — strictly better than today. The only worse-than-before state is the torn rekey of finding 2.

**Q4 — the inbox check's id: OK.** An adopted session keeps the wrist's own id: `_adopt` creates the phone's session with `id: sessionId`, the same id the converged snapshot and the inbox rows carry (`lib/state/watch/watch_session_adoption_bridge.dart:1107-1145`), and `holdsSession` matches on that id (lines 210-217). No rekeying of session ids was found in `lib/state`. The check at `session_core_lifecycle.dart:29-33` therefore reads the same id the wrist rows carry. The other two D-11 clauses do not depend on the id at all, so even an id mismatch would be caught by them for a session the wrist ran.

**Q5 — the three docs: Minor (finding 1) plus the rows below.** `workout_state.md`'s endSession row matches the code clause by clause (drop first, three skip clauses, store read, position + 1 or skip marker, descending order, rekey as `deleteEntry` does, effort removal, timed/drill/round untouched, never blocks the end) and every test it names exists: `S-15701`..`S-15717` all appear in `test/finish_drops_unlogged_sets_test.dart` (lines 92-512, including S-15714/15/16/17 beyond the plan's list) and `S-15709` in the screen test. `rest_tracking.md`'s paragraph matches D-2/D-11 and names an existing test file. `deleteEntry` exists (`lib/state/workout/session_core_entry.dart:684`). `session_summary.md`'s S-15708/S-15709 citations exist and the figures claim matches S-15708; only the exercise clause is overbroad (finding 1). No other stale term in the three docs.
