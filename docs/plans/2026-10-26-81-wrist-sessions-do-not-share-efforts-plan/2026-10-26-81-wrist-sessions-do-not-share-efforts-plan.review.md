## Findings

1. [Minor] lib/state/watch/watch_sync_request_handler.dart:226-236 — `_foodsFrame`'s empty-cache branch trusts `_foodsReadOk`, but the food cache can be emptied by a `loadFoods`/`loadFoodGroups` call from outside the handler (`lib/features/nutrition/nutrition_screen.dart:77-78`, `lib/features/nutrition/add_food_screen.dart:90` — the latter unawaited) landing during the awaits between the handler's own reload and the frame build (`buildRoutinesDown` at :152-155, and inside `_bundle` at :243-251): the flag then says "read ok" of a cache it no longer populated, and an empty `foods_down` tells the wrist "no foods" while the phone holds foods — plan 83 D-4's own rule ("only a read that succeeded may say no foods") broken by the interleaving. Fix: evaluate the foods frame immediately after `_reloadFoods` returns and pass that value into both `referenceText` and `_bundle`, instead of re-reading the live cache after further awaits. Guard: a handler test that fails the repository read from a concurrent `loadFoods` between the reload and the frame and asserts no empty `foods_down` is sent.
2. [Nit] watch/watchos/Sources/WatchSessionEngine/WatchPlatformWorkout.swift:318 + ios/OmniTrain Watch App/ContentView.swift:192 — `openFailed` is reset only inside `start`, so between a session change and the coordinator's refresh completing, the live closure `workoutNotice: { workout.openFailed }` (and the published `workoutOpenFailed`, assigned only after the refresh at ContentView.swift:288) still holds the previous session's failure: the first body evaluation of a later session's logging header can flash "Health workout didn't start" for one frame. Fix: clear `openFailed` in `apply`'s session-change branch (WatchPlatformWorkout.swift:398-401, where `openedForSessionId != session?.sessionId` already ends the old workout) before the lifecycle switch — the end-of-session summary is unaffected because there the session id is unchanged. Guard: a coordinator test that a refresh replacing a failed session with a new active one clears the flag even before the new begin's outcome exists.

2. **Plan 82 — no finding for the two asked scenarios; one Nit (finding 2).** A Free workout before its first exercise cannot show the header at all: the shell gates the logging surface on `!session.exercises.isEmpty` (ContentView.swift:460-462, 551), so the Start screen is up, and once the first exercise lands the same revision nudge runs `workout.refresh` → `WatchWorkoutLifecycle.action` → `.start` (the session has exercises, so `forSession` is non-nil, WatchPlatformWorkout.swift:376-389) → `start` resets `openFailed` as its first statement (:318) before the store is asked. An empty free session produces no summary (`guard !efforts.isEmpty`, :246). The residual is the one-frame transient of finding 2.
3. **Plan 83 — no finding for the asked mechanism; one Minor (finding 1).** `_foodsFrame` is never evaluated on a request whose reload was skipped or threw without a fresh flag: when `!storageUnchanged` the reload runs at :145 before `referenceText` (:156); when `storageUnchanged` the `since` gate re-runs `_reloadFoods` at :180 before `_bundle` (:181) — plan 83 D-5's claim, verified against the file. The only staleness is the out-of-handler interleaving of finding 1.
